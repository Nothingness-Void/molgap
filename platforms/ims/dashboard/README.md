# Always-on IMS dashboard

Choose a trusted always-on home Linux host first, or an explicitly approved VPS. Confirm IMS permits unattended SSH from its source IP, the 90-second cadence, jobinfo -c/-m/-w/-s, showlim -c, bounded reads of your V4 records under the resolved authorized root, and the listed fields leaving IMS for this host and Access provider. Confirm account policy, key restrictions, verified host fingerprint, approved hostname and individual viewer email before enabling collection. This service only reports status. The Windows launcher still provides the full local view.

## Install on the selected host after approval

Use Linux with systemd, OpenSSH client and Python 3.10+ at /usr/bin/python3. Python uses only its standard library. IMS needs bash, realpath, python3 and its scheduler utilities. Create a locked system account and group named ims-dashboard. Install the reviewed check_queue.py in a root-owned versioned release directory under /opt/ims-dashboard/releases and link /opt/ims-dashboard/current to that directory. Record its SHA256. Create /etc/ims-dashboard mode 0750 root:ims-dashboard. Have the owner provision a dedicated IMS-approved identity there at id_ed25519 (0600 owned by ims-dashboard). Install the independently verified IMS host key in /etc/ssh/ssh_known_hosts. Keep credentials outside releases. Use a separate restricted account for the reader (ims-dashboard-web, group ims-dashboard).

Install both adjacent .service files into /etc/systemd/system. Check them with `systemd-analyze verify /etc/systemd/system/ims-dashboard-*.service`, then `systemctl daemon-reload` and `systemctl enable --now ims-dashboard-web ims-dashboard-collector`. Only the collector starts SSH. One query times out after 45 seconds. After success it waits 90 seconds, after failure it doubles the delay up to 900 seconds. The reader marks data older than 240 seconds stale even if the collector stops. Confirm `ss -ltn` shows only 127.0.0.1:8765 and `curl -s http://127.0.0.1:8765/api/status` shows a successful snapshot. Keep inbound port 8765 closed.

## Configure access before routing

Create a [self-hosted Access application](https://developers.cloudflare.com/cloudflare-one/setup/secure-private-apps/private-web-app/) for the full exact hostname. Allow only the named email using the approved identity provider. Review all matching policies, including paths. Exclude bypass and broad allow rules. Only after verifying the policy, configure the named tunnel from cloudflared.yml.example, replace both UUIDs and hostname, validate with `cloudflared tunnel ingress validate`, install the connector as a system service and create its hostname route. Keep the final 404 ingress. Never route the Windows live endpoint. For private devices, [Tailscale Serve](https://tailscale.com/docs/features/tailscale-serve) with restrictive tailnet grants can instead proxy `tailscale serve --bg 8765`.

For Agent access, first demonstrate the actual client can send both custom headers to a controlled local test endpoint with dummy values and keep secrets out of logs. If supported, protect the exact /api/status path with its own Access application. Include the browser email policy there and a Service Auth rule for one expiring [service token](https://developers.cloudflare.com/cloudflare-one/access-controls/service-credentials/service-tokens/). Store the credentials in the client secret store. Send CF-Access-Client-Id and CF-Access-Client-Secret on each JSON GET. Leave machine access disabled if the client cannot do this.

## Acceptance and rollback

1. With Windows powered off, use a phone on mobile data. In a private browser verify both / and /api/status redirect to login or deny access without returning dashboard data. A different identity must be denied. Sign in as the permitted viewer and verify last-success time advances across collections.
2. From the Agent verify JSON fields and absence of raw logs, paths, usernames, node names and keys. Its token alone must fail at /. Multiple refreshes should leave the same last-success time until the next scheduled collection.
3. Temporarily block only the collector host’s IMS egress. Confirm the last successful rows and timestamp remain and the dashboard reports stale with an SSH fault. Restore egress and wait through backoff. Restart services and verify recovery from disk.
4. For upgrades, stage another versioned release, verify checksum and offline test first. Keep the previous release, unit files and sanitized status.json. Stop both services, switch current to the reviewed release, install matching units, daemon-reload and restart. Repeat acceptance. To roll back, stop services, restore the previous symlink and units, restore the saved snapshot if incompatible, reload and start. On authentication failure disable the tunnel route first and retain local-only service.
