# Post-release startup interpretation

The four immutable source packages, not later prose, own actual recipes. On
2026-10-22 the coordinator read all eight compiled recipes retained in the bound
workflow plans. Every arm used `four_stage_warmup_cosine_step`, warmup4,
15,620 updates and epoch-only logging. The frozen protocol's phrase "PPGT
cosine" omitted its staged warmup. This is a documentation correction, not a
schedule change or permission to replace an already submitted source package.
The original protocol, policy snapshot, compiled recipes and hashes are retained.

`TrainingLogger.start()` initializes counters but emits no START line. With
epoch-only logging the first `TRAIN_LOG` arrives only after a complete train
pass and its full Common-Dev evaluation. Preflight worker logs also remain in
their own files. Thus the observed gap after the isolated environment package
listing cannot establish that native admission is hung or that training has
not started. Conversely scheduler RUNNING cannot prove either admission or
optimizer progress. The next useful witness is a positive-step `TRAIN_LOG`,
or the independently retained native certificate/pair-state artifacts when
they become retrievable. A literal START marker is not required by this owner.

Luna's bounded owner-authenticated checks observed ESA1/PPGT1/PPGT2 RUNNING and
ESA2 QUEUED, without a terminal event. Log streams returned116 package-install
events then a connection timeout on three jobs; the queued job returned none.
These observations are not failed jobs, scientific results or retry authority.
Only exact bound job state and real output evidence may justify a next action.
