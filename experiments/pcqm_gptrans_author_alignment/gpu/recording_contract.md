# G1/G2 executable recording profile

Frozen on 2026-10-01 for the authorized independent input interventions.

The executable recipe is the unchanged accepted GPTrans V5 reference contract.
The new Spec, comparison prelaunch and per-arm plans bind the input intervention,
not a second optimizer or model family. The accepted CPU v2 path/state record is
the dependency authority; a COMPLETE scheduler response is insufficient.

Recording uses the previously qualified native `pcqm_gptrans_v4` V5 profile:
each arm has its own prospective trajectory/run ID, atomic checkpoint including
RNG/optimizer/scheduler/EMA, every-epoch live train/live development/EMA
development observations, exposure counters and checkpoint events. It retains
ten-epoch checkpoint chunks, selected EMA model, aligned development predictions,
completion hashes and optimizer-inclusive runtime qualification. The notebook
also records actual allocation and whole-job native wall/device cost, including
idle allocation; finalization must reconcile arm costs rather than charge the
whole two-device job twice.

The optional family-output profile is disabled for this screen. Its canonical
float64 target digest convention is not silently substituted for the immutable
reference's native float32 target manifest. This is reuse of the accepted native
V5 evidence profile, not real-remote qualification of the separate optional
family-output protocol. Native target tensors and their float32 digest semantics
remain unchanged.

Post-run acceptance must check each arm's receipt/version, actual source package,
Spec/arm binding, initialization, path digest where applicable, all 60 epochs,
46,860 optimizer steps, 5,998,080 sample presentations, selected EMA predictions,
row/target alignment, runtime, role history and native costs. It then constructs
actual paired analysis against the frozen V5 reference, the seven outcome
dimensions, immutable terminal records and canonical trace manifests. Both
candidate plans freeze the accepted reference ID. Replay qualification is a
post-run gate, never a prelaunch or job-summary assertion.

The request-to-action clock includes the CPU dependency/recovery and adapter
work. The separately measured qualified-package-to-POST clock starts only after
complete prelaunch and source/input verification. Neither a five-minute
end-to-end claim nor a scientific win follows from the local tests.
